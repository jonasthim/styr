# Styr v0.5 "Pipelines" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. One card per worktree; the orchestrator merges.

**Goal:** Chain agents. A pipeline is a small YAML DAG of steps; each step runs a template
(optionally in its own worktree), its structured report feeds later steps, lists fan out into
parallel steps, failures retry, and the UI shows the graph live with per-step transcripts.

**Architecture:** `internal/pipelines`: a YAML definition parsed into a validated DAG, a
pipeline run record with one step-run per node (fan-out creates N step-runs), and an executor
that advances the graph on the bus (`run.finished` events from the run engine): when all
dependencies of a node succeed, render its template with `steps.<id>.report` variables and
start a run via `runs.Engine`. Pipelines can be started by hand, by a trigger (template
selection widened to "template or pipeline"), or by a schedule.

**Constraints:** as before. Max 20 nodes, fan-out max 25 items, retries max 3, whole-pipeline
timeout default 2 h. Every step is unattended (service token, its template's profile).
Worktree per step: the pipeline's workspace must have worktrees enabled; steps that declare
`worktree: shared` reuse the previous step's worktree (sequential edits), `worktree: own`
(default) get a fresh one from base, and the last step's worktree survives for review.

## YAML definition

```yaml
name: fix-ci
workspace: styr            # workspace name; every step's template must use this workspace
timeout: 2h
steps:
  - id: triage
    template: "CI failure triage"          # template name (or template_id)
    with: { alert: "{{ .payload.title }}" } # extra vars rendered from the pipeline input
  - id: fix
    needs: [triage]
    template: "Apply fix"
    with: { plan: "{{ .steps.triage.report.proposed_action }}" }
    worktree: own
    retries: 1
  - id: verify
    needs: [fix]
    template: "Run tests and report"
    worktree: shared                        # continue in fix's worktree
  - id: review-each
    needs: [triage]
    foreach: "{{ .steps.triage.report.files }}"   # list → N parallel step-runs, item as .item
    template: "Review file"
```

Validation: unique ids, `needs` refer to earlier ids, acyclic, templates exist and belong to
the workspace, `foreach` and `with` are valid templates, limits above.

## Data model (migration `00008_pipelines.sql`)

```sql
CREATE TABLE pipelines (
  id TEXT PRIMARY KEY, owner_user_id TEXT REFERENCES users(id) ON DELETE CASCADE, name TEXT NOT NULL, workspace_id TEXT NOT NULL REFERENCES workspaces(id),
  yaml TEXT NOT NULL, created_at TEXT NOT NULL, updated_at TEXT NOT NULL);
CREATE UNIQUE INDEX pipelines_owner_name ON pipelines(COALESCE(owner_user_id,''), name);
CREATE TABLE pipeline_runs (
  id TEXT PRIMARY KEY, pipeline_id TEXT NOT NULL REFERENCES pipelines(id) ON DELETE CASCADE, origin TEXT NOT NULL, origin_ref TEXT NOT NULL DEFAULT '',
  input TEXT NOT NULL DEFAULT '{}', state TEXT NOT NULL CHECK (state IN ('running','success','failed','cancelled','timeout')),
  started_at TEXT NOT NULL, finished_at TEXT, cost_usd REAL NOT NULL DEFAULT 0);
CREATE TABLE step_runs (
  id TEXT PRIMARY KEY, pipeline_run_id TEXT NOT NULL REFERENCES pipeline_runs(id) ON DELETE CASCADE, step_id TEXT NOT NULL, index_in_fanout INTEGER NOT NULL DEFAULT 0,
  item TEXT NOT NULL DEFAULT '', run_id TEXT REFERENCES runs(id), attempt INTEGER NOT NULL DEFAULT 1,
  state TEXT NOT NULL CHECK (state IN ('pending','running','success','failed','skipped','cancelled')), report TEXT NOT NULL DEFAULT '',
  started_at TEXT, finished_at TEXT, worktree TEXT NOT NULL DEFAULT '');
CREATE INDEX step_runs_pipeline_idx ON step_runs(pipeline_run_id);
ALTER TABLE triggers ADD COLUMN pipeline_id TEXT REFERENCES pipelines(id);
ALTER TABLE schedules ADD COLUMN pipeline_id TEXT REFERENCES pipelines(id);
ALTER TABLE runs ADD COLUMN step_run_id TEXT REFERENCES step_runs(id);
```
`runs.origin` gains `pipeline`. Triggers and schedules accept either `template_id` or
`pipeline_id` (exactly one).

## Executor

- `Start(ctx, pipelineID, input Vars, origin, originRef)`: parse and validate the YAML,
  create the pipeline run and one pending step-run per node (fan-out nodes get their step-runs
  when their `foreach` list is known, i.e. when dependencies finish), then `advance`.
- `advance(runID)`: for each pending step-run whose dependencies are all `success` (for
  fan-out, all items of the dependency), render `with` and start a run via
  `runs.Engine.Start(RunInput{TemplateID, Origin: pipeline, Vars: input + steps.* + item,
  StepRunID})` in a session created on the pipeline's workspace; `worktree: shared` passes the
  dependency's worktree path (sessions gain `CreateInput.WorktreePath` to reuse an existing
  worktree instead of creating one). Mark running.
- On `run.finished`/`run.failed` for a run with `step_run_id`: success → store the report,
  mark success, `advance`; failure → if `attempt <= retries` create a new attempt step-run
  (same node, attempt+1) and start it, else mark failed and mark all downstream `skipped`,
  finish the pipeline run as failed. When no pending or running step-runs remain → success.
  Cost = sum of step runs. Timeout sweep like runs.
- `Cancel(runID)`: cancel running step runs (interrupt + close their sessions), mark
  cancelled.
- Triggers: `Deliver` starts a pipeline when the trigger has `pipeline_id` (Vars = normalised
  payload); schedules likewise.

## API

```
GET/POST /pipelines {name, workspace_id, yaml} → Pipeline (validated; 422 with a list of errors and line numbers when invalid)
GET/PATCH/DELETE /pipelines/{id}; POST /pipelines/validate {yaml, workspace_id} → {ok, errors[], graph: {nodes, edges}}
POST /pipelines/{id}/start {input?} → 202 {pipeline_run_id}
GET /pipeline-runs?pipeline=&state=&limit= ; GET /pipeline-runs/{id} → {run, pipeline, steps: [StepRun with run summary], graph}
POST /pipeline-runs/{id}/cancel → 202 ; POST /pipeline-runs/{id}/retry-failed → 202 (re-runs failed step-runs and continues)
Triggers/Schedules: `pipeline_id` alternative to `template_id` in inputs and responses.
SSE: `pipeline.state` frames {pipeline_run_id, step_run_id?, state}.
```

## Frontend

- **Pipelines page** (`/pipelines`, rail item, palette): list (name, workspace, steps count,
  last run state, Start), YAML editor page (`/pipelines/$id`) with a live graph preview from
  `/pipelines/validate` (React Flow via `@xyflow/react`, nodes = steps with template name and
  worktree mode, edges = needs; fan-out nodes drawn with a stacked outline), validation errors
  inline with line numbers, a Start dialog with an input JSON editor, and a "New from template"
  starter (sequential two-step skeleton).
- **Pipeline run page** (`/pipeline-runs/$id`): the graph live (node state glyphs pending/
  running/success/failed/skipped/cancelled, retry badge with attempt number, fan-out nodes
  show n/N done), click a node → side panel with the step's report and a link to its session
  transcript; header with state, elapsed, cost, Cancel, Retry failed; per-run log list below
  (step, attempt, started, duration, outcome).
- Runs page: pipeline runs appear as a third tab; run detail shows "Step of pipeline <name>".
- Triggers and schedules dialogs: "Run a template" | "Run a pipeline" selector.
